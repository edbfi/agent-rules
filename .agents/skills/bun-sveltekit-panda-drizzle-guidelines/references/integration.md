# Integration and verification

## Build and generate in dependency order

The runnable [example project](../assets/examples/package.json) contains exact pins, Kit/Vite/Panda configuration, reactive components and API inputs. Its generated styled-system and SDK directories are ignored; the source is compact and regeneration is part of the check. For a fresh checkout run `bun install`, `bun run generate` and `bun run db:generate`; the last command creates both dialect migration histories needed by the tests. Then run `bun run check`, `bun run build`, `bun run lint`, `bun run format:check` and `bun test`. Migrations are generated locally for this source template; an adopted application reviews and commits its migration history. Start the example with `bun run start` after building and open `http://127.0.0.1:3000`, matching its compiled canonical origin; a different host, scheme or port requires updating APP_ORIGIN and rebuilding.

The dependency order is Kit sync → Panda/Hey API generation → Svelte/TypeScript checking → production build. Both generators can resolve the inherited tsconfig; running them before sync in a fresh checkout can fail. Vite's Panda plugin handles ongoing CSS generation, while explicit codegen makes imports/types available to standalone tools. [Kit sync](https://svelte.dev/docs/kit/cli), [Panda Vite](https://panda-css.com/docs/get-started/vite), [Hey API generation](https://heyapi.dev/docs/openapi/typescript/get-started).

Use the root ESLint/Prettier assets as a starting point and adapt generated-output ignore paths. The flat Svelte ESLint parser uses the TypeScript parser without resurrecting a rejected svelte.config file. Ignore generated implementations for lint/format where appropriate; do not hide handwritten server or component files behind a broad ignore. `skipLibCheck` is not a replacement for checking application code. [Svelte ESLint](https://sveltejs.github.io/eslint-plugin-svelte/user-guide/), [Prettier Svelte](https://github.com/sveltejs/prettier-plugin-svelte).

## Isolated database verification

For SQLite tests use a unique temporary directory per test. Apply generated SQLite migrations, assert data behavior, close, reopen and assert persistence. Verify foreign keys on the connection. Assert rollback by making the transaction fail after a first write, then querying that no partial change survived. Remove the owned directory after closing so SQLite sidecars cannot escape cleanup. [Bun SQLite](https://bun.sh/docs/api/sqlite), [SQLite foreign keys](https://www.sqlite.org/foreignkeys.html).

For PostgreSQL use a fresh PostgreSQL 18.6 container/database owned by the test run. Keep test credentials separate from application credentials and never run cleanup against a supplied shared database. The example [compose file](../assets/examples/compose.yaml) pins that server and uses ephemeral storage. Choose a unique project name, start it with `docker compose -p guide-check-UNIQUE up -d --wait`, then run `REQUIRE_POSTGRES=1 TEST_DATABASE_URL=postgres://guide:guide@127.0.0.1:55432/guide bun test postgres.test.ts`. Use `docker compose -p guide-check-UNIQUE down --volumes` afterward for that same owned project. Run `bun run db:generate` first if the local migration folders do not exist. Override GUIDE_PG_PORT if the example port is already occupied. Without the URL, the default Bun suite explicitly skips the PostgreSQL test; it does not imply PostgreSQL coverage. Apply migrations twice, run transaction/concurrency checks and close pools before removing the service. SQLite passing does not verify the PostgreSQL dialect, server constraints or network behavior. [PostgreSQL testing semantics](https://www.postgresql.org/docs/18/transaction-iso.html).

## Browser and validation gates

Run a real production browser check for hydration, Ark keyboard/focus behavior and Panda computed styling. After building the example, `bun run test:browser` checks hydration, Dialog validation/Escape/focus restoration, Panda padding, action/API responses and private sentinel absence from SSR/page HTML. Extend that check with focus containment, navigation data and served client asset inspection when those boundaries change; the included check does not claim to test those extra surfaces. Component compilation alone cannot prove those properties. Verify that private environment sentinels are absent from SSR HTML, serialized page data and served client assets; inspecting only the source import graph misses deliberate serialization. Exercise form validation and API non-2xx/empty paths. [Kit server-only boundaries](https://svelte.dev/docs/kit/server-only-modules), [Playwright assertions](https://playwright.dev/docs/test-assertions).

The shared [check script](../scripts/check.sh) takes a project directory and runs real compiler/build, lint and format commands with the selected toolchain. Set `EVAL_REQUIRE_TESTS=1` when the task asks for tests. For an existing project preserve its actual test runner rather than replacing meaningful tests with a smoke test. A no-op lint/test script is not validation. Report the commands and behavior actually checked, including any service or browser mode that was unavailable.
